# Wire protocols

SÜRÜ ingests two framings. They look superficially alike — a magic byte, a length, a payload, a
16-bit CRC — and they are not compatible in any of the details that matter.

## MAVLink v2

```
 0xFD | len | incompat | compat | seq | sysid | compid | msgid(3) | payload(len) | crc(2) [ | signature(13) ]
```

- Header is 10 bytes including the start byte; message id is 24-bit little-endian.
- The signature block is present exactly when `incompat & 0x01`. Getting this wrong costs you the
  *next* frame, not this one, which is why it is easy to miss.
- A sender may drop trailing zero bytes of a payload, so `len` is frequently shorter than the
  message's declared length. Missing bytes are implicitly zero.

### MAVLink v1

```
 0xFE | len | seq | sysid | compid | msgid(1) | payload(len) | crc(2)
```

Same checksum rule, 6-byte header, 8-bit message id. Both versions can appear on one link.

### Checksum

**CRC-16/MCRF4XX** over everything from `len` through the end of the payload, then one further
byte: the message's `CRC_EXTRA`.

`CRC_EXTRA` is a hash of the message's field definitions. Its purpose is to make a version
mismatch fail loudly: two peers that disagree about a message's layout produce different checksums
and reject each other, instead of quietly misreading fields. The practical consequence is that
**a frame cannot be validated without knowing the message** — see `MavlinkDialect`.

> **This is not CRC-16/X-25.** The reference C implementation names its function `crc_accumulate`
> and its seed constant `X25_INIT_CRC`, so the X-25 entry in the CRC catalogue looks like the right
> one. It is not: X-25 finishes with a final XOR of `0xFFFF` and MAVLink does not. For the standard
> check input `"123456789"`, MCRF4XX yields `0x6F91` and X-25 yields `0x906E`. A decoder built on
> the wrong one rejects every frame it ever sees.

### Dialect

ArduPilot emits messages beyond the `common` set, so the `ardupilotmega` dialect is required. On
`common` alone those frames cannot be checksummed at all — and the official C library reports them
as `BAD_CRC`, which makes a perfectly healthy link look corrupt and skews sequence-loss statistics.
`MavlinkDecoder` counts them as `unknownMessages` instead, kept apart from real corruption.

The table lives in `ArduPilotMegaDialect`, generated by `tools/generate-mavlink-dialect.py` from the
MAVLink C headers. It is generated rather than transcribed because it holds several hundred entries.

## ÇARGE capsule log ('HK')

```
 'H' 'K' | ver(1) | type(1) | len(1) | payload(len) | crc16(2)
```

Written to an SD card by the ÇARGE capsule firmware (`App/services/storage/storage.c`), little-endian
throughout, no padding between payload fields.

### Checksum

**CRC-16/CCITT-FALSE** over `ver..payload` — that is, everything between the magic and the checksum
— stored little-endian.

Both protocols use polynomial `0x1021`, and that is where the similarity ends: CCITT-FALSE is
MSB-first and non-reflected, MCRF4XX is reflected (effective polynomial `0x8408`). Neither can
validate the other's frames.

### Record types

| Type | Code | Payload | Contents |
|---|---|---|---|
| META | 1 | 8 B | boot time, firmware version, reset cause, log format version |
| ENV | 2 | 41 B | time, mission state, pressure, altitude, 3 temperatures, 2 humidities, battery |
| IMU | 3 | 36 B | time, 3-axis accelerometer and gyroscope, derived roll and pitch |
| GPS | 4 | 35 B | time, latitude/longitude as doubles, altitude, speed, course, satellites, fix |
| EVENT | 5 | 8 B | time, mission state transition, argument |

Mission states, in order: `BOOT`, `SELFTEST`, `ATTACHED`, `ARMED`, `RELEASE`, `DESCENT`, `LANDED`,
`RECOVERY`.

## Resync

Both decoders recover the same way, and the rule is the same in both: **on any failure, advance
exactly one byte and rescan.** Never skip by the length field the failed frame claimed.

This is not caution for its own sake. A corrupted length byte is indistinguishable from a valid one
until the checksum fails, and by then trusting it would have skipped over however many real frames
followed. `MavlinkDecoderTest.survivesCorruptedLengthField` pins this down.

Garbage on the wire is normal, not exceptional:

- An ArduPilot board prints a **text boot banner** before it starts framing. The recorded SITL
  stream used in the tests opens with 119 bytes of `Init ArduCopter V4.6.3 ...`.
- Joining a live link mid-stream lands in the middle of a frame.
- A capsule that loses power mid-write leaves a **torn tail**, and a damaged region in the middle of
  a card must not cost the records after it.

A subtler case, which the fixture deliberately contains: a bare `HK\x01` spliced into the stream is
not merely unrecognised — it *parses*. The following frame's own magic supplies a plausible type and
length, so the decoder reads a frame-shaped span and only the checksum rejects it. Recovery by one
byte then finds the real frame.

### Streaming versus end of stream

Mid-stream, a frame that runs past the buffered bytes is simply incomplete: the decoder holds it and
waits. Once the link closes or a file ends, that same shape is garbage and gets resynced past.
Callers mark the difference with `endOfStream(handler)` — which is also what makes these decoders
agree byte for byte with the reference implementations under `tools/`.

## Verification

Both decoders are differential-tested against independent implementations rather than against
themselves:

- `tools/hk-reference.py` — a transcription of the decoder written against the capsule firmware.
- `tools/mavlink-reference.py` — written from the MAVLink specification.

Both emit a canonical dump in which floats appear as raw IEEE-754 hex. Printing decimals would have
compared Java's rounding against Python's (half-up versus half-even) instead of comparing what was
read from which offset.

The MAVLink oracle is run over a genuine 36 KB SITL recording: 1058 frames, 30 message types, zero
checksum errors, zero unknown messages, 119 bytes of banner resynced at the head. The Java decoder
must reproduce that file exactly, under every input chunking from one byte upward.
